# 示波器操作比賽：Haiku 5.5（effort max）對 Opus 5.5（effort medium）

2026-10-12 用 Keysight DSO-X 4034A 的內建 Demo 訊號做的。問題是：在答案正確的前提下，改用 Haiku 5.5 Max 操作示波器會不會比 Opus Medium 快。

**結論：不會。** 五題兩邊都答對，但 Opus Medium 總共只花 412 秒，Haiku Max 花了 1999 秒，慢 4.9 倍；讀進的 tokens 也是 Opus 的 3.2 倍。慢的原因不是試錯，而是 Haiku 在 effort max 下每一步都想很久（每次回應平均 16–34 秒，Opus 是 3–5 秒），而且多讀了好幾個說明檔。以目前的設定，操作示波器請用 Opus Medium。

## 方法

- 主 session（Opus 5.5）當裁判，用 subagent 執行：一個指定 `model: haiku, effort: max`，另一個指定 `model: opus, effort: medium`，`subagent_type` 都是 general-purpose。每題每個模型各跑一次（n=1）。
- 示波器只有一台，所以一次只跑一個 agent。每場開始前，裁判腳本把示波器重設成同樣的起始狀態：Demo 關、CH1 1 V/div、1 ms/div、EDGE CH1 準位 0 V、AUTO、游標關。T5 例外，見下表。
- 先後順序輪流：T1、T3、T5 由 Haiku 先跑，T2、T4 由 Opus 先跑。
- 兩邊的 prompt 一字不差，只描述硬體與接線（CH1→Demo 1、CH2→Demo 2，10:1 探棒）、任務內容和最後一行的 JSON 格式。沒有提示 MCP 名稱或 wiki。
- 評分不採信模型的自我報告。裁判先自己量一組標準答案，事後直接讀示波器的最終狀態，再比對模型回報的數值。
- 時間取完成通知的 `duration_ms`，tokens 取 `subagent_tokens`。transcript 另外拆成兩部分：「模型時間」是從工具結果回來到模型下一個回應的時間，「工具時間」是工具實際執行的時間。

### 題目與判定

| 題 | 任務 | 判定標準 |
|---|---|---|
| T1 置中截圖 | 開 CLK；CH1 垂直置中，占畫面一半到四分之三且不削頂；顯示 2–3 個週期；上升緣、50 % 觸發；拍白底截圖；回報頻率與 Vpp | 頻率 ±2 %、Vpp ±10 %；畫面 1.5–4 個週期；波形高 3–8 格且不削頂；中心偏差 ≤0.5 格；準位落在擺幅 40–60 %；截圖檔是新的 |
| T2 游標上升時間 | 放大上升緣（≤50 ns/div）；游標標 10 %／90 %；和自動量測對照；游標留在畫面上 | 回報值與示波器上游標的 ΔX 都在 ±15 % 內；自動量測值 ±10 % |
| T3 雙通道相位 | 開 PHAS，量 CH1→CH2 延遲與相位 | 延遲絕對值 ±5 %；相位 ±3° |

### 合計

| | Haiku Max | Opus Medium | Haiku／Opus |
|---|---:|---:|---:|
| 正確題數 | 5／5 | 5／5 | — |
| 總時間 | 1999 s（33.3 分） | 412 s（6.9 分） | **4.9×** |
| 不含 T4 的總時間 | 1529 s | 165 s | 9.3× |
| 單次回應平均思考時間 | 16–34 s | 3.4–4.8 s | 約 5–8× |
| 各題 `subagent_tokens` 加總 | 754,145 | 243,722 | 3.1× |
| 累計讀進的 tokens（含快取） | 9.31 M | 2.95 M | 3.2× |
| 工具呼叫加總 | 136 | 120 | 1.1× |

工具呼叫次數相差不大，但耗時差了將近 5 倍，所以差距幾乎全來自模型本身的思考時間，不是在示波器上反覆試錯。Haiku 每場的工具時間只有 8.5–51 秒，模型時間卻有 222–475 秒；T3 有一次回應想了 210 秒。

## 觀察

**Haiku Max**
- 五題都答對，T5 陷阱也一次就看懂：它察覺準位 3 V 高於約 2.1 V 的訊號，改成 1.05 V 後才量。
- 每一場開頭都先讀說明檔（`keysight.py`、`ks_mcp.py`、`LLM_WIKI/keysight-scope.md` 等），每場 3–14 次 Read／Glob／Grep／shell。這是「只給任務」的代價，Opus 則直接從工具說明開始操作。
- T3 的數值正確，但它把延遲正負號解讀反了，說「正值代表 CH2 領先」。裁判看截圖確認：CH1 峰值在 +240 µs，CH2 在 +490 µs，所以是 CH2 落後 CH1 約 250 µs，Opus 的解讀才對。如果下游要靠這段文字判斷相位方向，就會出錯。
- T2、T3、T4 為了不在專案的 `captures` 寫檔，它刻意不截圖也不擷取波形。它其實分不太清 MCP 部署資料夾（`~/.claude/mcp/keysight/captures`）和專案資料夾。
- T4 中 `jev_diagnose_capture` 在 GLITCH＋AUTO 的平線畫面上回報 `wiring`（信心 0.41–0.51），它自己判定為誤判，沒有被帶偏。

**Opus Medium**
- T1、T2、T3、T5 都在 34–53 秒內完成，7–9 次回應，沒有讀任何檔。
- T4 是這次唯一明顯的試錯：起初沿用 autoscale 的 1.25 V 準位，剛好和 glitch 約 1.31 V 的峰值差不多，所以一直觸發不到。它試了多種設定（66 次工具呼叫），其中 3 次 `ks_capture` 卡住，由 MCP 自動解除，最後改成 0.6 V 才抓到。即使這樣，它還是比 Haiku 快 1.9 倍。
- T4 暴露出 MCP 的一個問題：單次觸發已經 arm、還沒等到觸發時呼叫 `ks_capture(mode=RAW)`，它會先 `:STOP` 再讀，但仍然卡住，要靠 VXI-11 clear 解除。可以讓 `ks_capture` 在「停止但沒有資料」時直接拒絕。這次沒有改。

## 結論與建議

1. **在正確為前提下，Haiku 5.5 Max 不會比較快。** 兩邊正確率相同（5／5），Opus 5.5 Medium 總時間少 79 %，tokens 少 68 %。effort max 讓 Haiku 每一步都長時間思考，抵消了它 token/s 較快的優勢。
2. **以後操作示波器（以及之後的 F280049C 量測）預設用 Opus Medium。** 標準操作（置中、截圖、游標、雙通道、處理卡住的觸發）大約 35–55 秒一題。
3. 如果還想試 Haiku，應該試**較低的 effort**（low／medium），而不是 max。這次沒有測，不能斷定會比較快；如果要測，用同一套腳本再跑一輪即可。
4. 需要判斷方向或因果的結論（例如相位誰領先、哪條線接錯），不要只信 Haiku 的文字說明，要用數值或截圖核對。
5. 不論用哪個模型，在 prompt 裡寫明「用 keysight MCP，細節見 `LLM_WIKI/keysight-scope.md`」，可以省掉 Haiku 開場讀檔的時間。這一點這次沒有量。

## 限制

- 每題每模型只跑一次。T4 這種需要摸索的題目，同一個模型重跑一次的時間可能差很多。
- 跑的是 subagent，不是主 session，系統提示和主 session 不同。
- 訊號源是 Demo 訊號，不是 F280049C。
- transcript 裡 Opus 的 output token 數看起來不完整，所以 tokens 只比較 `subagent_tokens` 與累計讀進的 tokens，不比較輸出量。
- 每場結束後，裁判把示波器還原到實驗前抄下的還原點。逐項比對沒有差異，錯誤佇列也是空的。

裁判腳本（重設、標準答案、評分、transcript 分析）放在工作階段的 scratchpad，沒有放進 repo。
